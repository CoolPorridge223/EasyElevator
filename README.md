# EasyElevator

Minecraft **1.21.1** · Fabric Loader **0.19.2** · Fabric API **0.116.17+1.21.1** · Java **21**。

当前模组版本 **2.2.1**。六个组件：电梯轨道、楼层电梯门，以及四种电梯轿厢（普通／高速／观光／强力）。四种轿厢共用同一个父类 `entity/AbstractCabinEntity`，彼此只差**速度**、**限载人数**与**外观**三项，运动、门联锁、载客与存档完全同一份实现。模型与材质已经做到**内饰级细节**（外壳、踢脚线、不锈钢扶手、顶棚灯槽与自发光顶灯、门口金属门槛与门楣轨道、操纵面板的边框/面板/显示窗/按钮，以及轨道底座螺栓与门楣显示屏），轿厢与门框各有自己的贴图，到站默认播放内置音效，支持按楼层选择或上传音频；运行音默认静音，开关门不发声。

## 2.2.1 更新

- 新增**强力电梯轿厢**（`easyelevator:powerful_cabin`）：外壳、门、速度与井道尺寸都与普通轿厢**逐位相同**，但限载 **20 人**。
- 强力轿厢的**内饰换成重载套装**（保留普通轿厢的全部内饰，另加）：上下**两道**不锈钢扶手、后壁两根立柱、门口一侧的**第二块顶灯**、后壁的**载重铭牌**（上面用红字写出限载人数）、门槛内侧的**防滑钢踏板**。物品图标是红色负载板，带三个人形图案。
- 门口那块顶灯**真的会照亮门口一带**：强力舱的舱内补光改用双灯采样（取两盏里更亮的一盏，上限仍是 13 级），另外三种型号的舱内观感**逐像素不变**。
- **超载保护**：厢内玩家数超过限载时，轿厢进入「超载」——门保持全开、不再派发行程，轿厢内的模拟面板与选站面板状态行都显示"超载"，直到有人走出厢门。普通／高速／观光三型**不限载**（限载 0 = 不限制），行为与之前完全一致。
- 配方：5 个铁锭 + 2 个铁块 + 1 个红石块 + 1 个活塞（比普通轿厢更重）。
- 模型与贴图生成脚本现在**同时拥有**强力轿厢的红色负载板与图标；`python tools/generate_art.py` 会额外断言"强力内饰保留普通内饰的每一件"。
- 修复：**轿厢刚放到轨道上、还没建任何楼层门时，门一关人就出不来了**（开门键在那条线路上不可用）。现在"这条线路上一扇完整的门都没有"也算可开门的情形之一——车本来就永远不会动（没有站点可去），必须让乘客能自己走出来。
- 修复：上面那条判据一度让**客户端的开门键永远亮着**（运行时也亮，点下去被服务端拒绝并提示"只在停在某一层时有效"）。原因是客户端拿不到线路（`railX/railZ` 不同步），判据改回"只吃同步数据 + 面板站点列表"的纯函数，运行途中按键照旧变灰。
- 修复启动日志里的 `No data fixer registered for easyelevator:xxx`（四个轿厢各一条，开发环境还会直接崩在模组初始化）：注册实体类型时用了原版带 id 的 `EntityType.Builder.build(String)`，它会先向原版数据修复器查这个 id 的 choice type，而模组 id 不在原版 schema 里。改用 Fabric 的无参 `build()` 后该报错消失，**实体 ID、存档与行为完全不变**。
- 存档格式不变，服务端与客户端可以和其他 2.2.x 混用（新物品只是新增，旧存档里的轿厢行为不变）。

## 搭建和使用

1. 从创造模式「简易电梯」物品栏取出六个组件，或使用配方合成。
2. 垂直放置一列连续轨道。第一块轨道朝向放置者，后续上下延伸会继承方向。**轨道朝向是轿厢所在方向，也是轿厢门朝向**。
3. 在轨道朝向前方 **3 格**、同一 Y 高度，放置电梯门的**底部中心**。一件物品自动生成 **3 格宽、3 格高**的整扇门，预留完整空间。距离按方块坐标计算，不是中间空出3格。每扇完整门对应一个站点，按高度排序。
4. 手持任意一种「电梯轿厢」，右键任意一块轨道。轿厢中心位于该轨道朝向的前方 2 格；底部 Y 与被点击轨道相同。预留 **3×3 的井道、3 格轿厢高度**，整个运行区间清空。每段连续线路只能放置一个轿厢（四种型号一起计数：同一条线路上再放第二种会被拒绝）。
5. **右键楼层电梯门**：不再直接呼叫，而是弹出**厅外呼叫面板**——**同尺寸的小方块**竖排成一列：**▲（上行）**、**▼（下行）**、**×（关闭）**（悬停显示"关闭"）。**端站只显示有意义的方向**：最底层下面没有站点，只显示 ▲；最顶层上面没有站点，只显示 ▼；中间层两个都在。按下方向键后服务端登记这条带方向的呼叫，按钮随即**变红**并一直亮着，直到轿厢真的到站开门那一刻才熄灭（关掉面板再打开也能看到它仍然红着）。没有轿厢到达这一层时，楼层门保持关闭，具有实际碰撞；到站并开始开门后开放，轿厢门关闭完毕、运行前重新锁闭。
6. **潜行右键楼层电梯门**：弹出**这扇门专属的设置面板**（见下面「每扇门自己的门音效设置」一节）。原来"潜行右键 = 直接把这一站设为基准层"的功能，现在变成面板里的**「设为基准层」按钮**，判据与效果逐条保留：把这一站设为整条线路的**基准层（1 层）**——它下方的站点依次显示 **B1、B2……**，上方的依次显示 **2、3……**。轿厢内的选站面板、轿厢内面板与所有楼层门框顶部的层号会立刻按新编号显示。默认（没有设置基准层时）仍然是最底层 = 1 层；把基准门拆掉也会回到默认编号。**普通右键**照旧是厅外呼叫面板，本次改动没有碰它。
7. 进入轿厢后，对着轿厢**任何地方右键**都能打开选站面板（**与手里拿什么无关**：空手、拿着方块或物品都一样；也不再要求准星对准操纵面板）。面板内容：站点排成一整块方形数字按键（模拟真实电梯面板），编号按高度从 1 起、**最底层为 1 层**（设了基准层后按第 6 条编号）；按钮从**右下角**起步，先**从右往左**、再**从下往上**排列，列数自动选成尽量长方形，站点较多时用底部的 `<` `>` 翻页。悬停显示站点与高度；**轿厢当前停靠层**的按键为绿色描边，**已加入停靠计划**（正在前往或已排队）的按键为红色描边——绿色与开门键都只在轿厢**停稳**后出现，运行时经过楼层不会闪一下。面板自上而下分成**表头条**（标题 + 左上角楼层指示牌 + 右侧"高度 / 页数"）、**按键区**（比面板更暗的凹底托住整块数字键）、**页脚条**（翻页 / 开门 / 关门 / 完成），三条色带之间用 1 像素分隔线断开；面板底**不透明**，井道里的红字不会从底下透出来。楼层指示牌为**深底红字、放大 2 倍、只显示层号本身**如 `3` / `B1`，不再写"第 n 层"，与右侧的"高度"行、"n 个站点"行并排，每经过或到达一层更新一次；同一个层号还用红字显示在**楼层门框顶部**与**轿厢内的模拟面板**上——轿厢面板是两行（**第一行是闪烁的方向箭头、第二行是到达层数**），门框则是横向一行（左边箭头、右边层数，整组居中，例如"▲ 3"）；箭头只有**正在运行时**才出现——**上行 ▲、下行 ▼**，**停靠（含开门、暂停）时留空**，并且**一亮一灭地闪烁**（亮 0.5 秒 / 灭 0.5 秒，门框与轿厢面板同相）。运行状态由已同步的相位与目的站推导，不需要额外同步字段。底部另有**开门 / 关门**键：**开门**会把**正在关闭的门反向重新打开**（中断关门）、也能把已关好停在本层的门重新打开，门已全开时相当于按住开门键延长停留——它**只操作门，不会把本层排进呼叫队列**，因此不会出现"先开走、之后再回来"；**关门**会立刻结束停留并关门，队列里还有目的站时随后出发。两个键都只在轿厢停稳在某一层时有效（运行途中经过楼层时按不动）。面板取消背景模糊，使用轻微暗色遮罩，游戏画面与文字保持清晰。选择后由服务端重新检查整扇门及线路，随后入队。
8. 无人乘坐时，在轿厢外**空手潜行右键**回收轿厢。**门打开时**站厢内朝门外看，门外的方块照常拆/放（左键破坏、右键放置都正常，与手里拿什么无关）；**门关着时射线不穿透轿厢**，点不到外面的方块。**门槛只有三条：潜行、主手空着、且厢内没有任何乘客**（玩家或生物；判据是 `containsPassenger`，你自己站在厢内时就算一名乘客，所以这也等于要求人在轿厢外）——**不看**轿厢当前在不在跑、门正在开还是关、有没有未完成行程，满足就回收，生存模式返还**本型号**物品。生存模式拆掉楼层门任意一部分，整扇门一起移除，只返还一个门物品。

### 呼叫调度：方向、顺路与停靠顺序

- **轿厢内选站**是"目的层"，没有方向，任何行程方向都能服务；**厅外呼叫**带方向，只有**正在按该方向运行**的轿厢才会顺路接走（现实电梯的集选控制）。例如车在 1 层上行时，5 层的"上行"与车内的 8 层会依次停靠，而 8 层的"下行"要等车到顶掉头下行时才接。
- 停靠按**运行方向上的位置顺序**，不是按键先后：上行途中不会越过同一方向的楼层再去更远的那层；**运行途中新插入的同方向更近请求会被立刻插到前面**（正驶向 10 层时有人在 5 层按了上行，轿厢会先在 5 层停，而不是径直开过）——插入时队列即按服务方向重排，面板上的"停靠计划"顺序就是实际停站顺序。请求全部完成后轿厢停车待命，服务方向复位为空闲。
- 反方向的孤立呼叫（例如车在 1 层、8 层按下行）也会被服务：轿厢会空车上去接他——不会因为方向不一致而永远等不到车；到站开门只清掉**与本次服务方向一致**的那条呼叫（按钮随之熄灭）。
- **服务方向 = 轿厢实际要开的方向**（不是按钮的方向）：空车去接反方向呼叫时，沿途凡与轿厢同向的厅外呼叫都会被顺路接走。
- **方向记忆**：轿厢停车开门等乘客时会**保留刚才的服务方向**——被下行呼叫叫到 5 层、进厢后按 6 层、而楼下还有呼叫时，轿厢先把这一趟跑完（下到 1 层接人）再上行去 6 层；**只有当前方向的前方再也没有请求**时才会掉头（五层以下无人呼叫时才直接上行）。例如车在 10 层、底层按"上行"、二层按"下行"：轿厢向下开，途中先在二层停下接"下行"的乘客，再到底层——不会一路开到底层再折返二层（顶端站同理）。
- **同一层的上行与下行呼叫各自独立**：到站开门只熄灭"这一趟服务方向"的按钮。所以 2 层同时按了上行和下行时，上行到达只熄上行那盏灯，**下行那条会一直亮着**，等轿厢回头下行再来接。
- **先来先服务**：轿厢空闲时被派往的目的地永远是**最早登记的那条呼叫**，不是最近的那条——1 层先按"上行"、2 层随后也按"上行"时，轿厢先下到 1 层，再顺路上来接 2 层；后登记的**反方向**呼叫永远不会半路抢走目的地（运行途中只有**同方向**的呼叫能被顺路接走）。顶端站镜像同理：顶层先按"下行"、中间层随后也按"下行"时，先到顶层再顺路下行接中间层。
- 厅外呼叫随轿厢一起存档（站点坐标 + 方向 + 当前服务方向），读档后继续服务；楼层门被拆时该站的呼叫自动取消。

### 楼层编号：基准层与地下层

- 默认编号：站点按高度升序，**最底层 = 1 层**，向上 2、3……
- **潜行右键**任意一扇楼层门，在弹出的**门设置面板**里点**「设为基准层」**，即把它设为**基准层 = 1 层**：比它低的依次显示 **B1、B2……**（内部用负数表示），比它高的依次显示 **2、3……**。设置写在那一扇门的方块实体里，随区块存档；一条线路最多一扇门带这个标记，在别的门上再点一次「设为基准层」就会改基准；在基准门上再点一次即取消（回到"最低层 = 1 层"）。
- 三处显示同源：轿厢内选站面板的按钮编号、轿厢内面板的层号、所有楼层门框顶部的层号，全部来自同一个 `logic/FloorIndicator`，因此不会出现"面板显示 B1、门框显示 0"这类分叉。

### 每扇门自己的到站音效设置

**潜行右键**任意一扇楼层电梯门，打开这扇门的专属设置面板。面板管的是这扇门的**到站提示音**——轿厢精确停在这一站时响什么。**设置按门独立**：同一栋楼里大堂那扇门可以响一声铃、设备层可以安静，互不影响。

| 面板上的控件 | 作用 |
| --- | --- |
| **到站音效**（左端开关） | 这一站到站时是否发声。出厂默认**开 + 默认音效**，与模组原有的"到站必响一次"完全一致——**旧存档的门升级后照旧会响**（缺失的存档字段按出厂默认读回），不需要逐扇重设；默认设置的门不写任何存档字段，旧存档体积也不变 |
| **音效名** | 当前选中的音效：默认音效 / 自定义文件 / 预设原版音效 |
| `<` `>` | 循环切换音效选项：**默认音效 → 自定义文件 → 6 组预设原版音效**（钟回响、紫水晶风铃、音符盒铃、音符盒叮、经验球、末影之眼）→ 回到默认。切换不会改动开关 |
| **选择文件…** | 备用入口：尝试弹系统文件对话框挑一个本地 `.ogg`（≤ 512 KiB）。**推荐直接把 `.ogg` 拖进游戏窗口**，不依赖任何对话框 |
| **试听** | 让服务端用权威音效当场播一次；值格会闪一下并显示 `▶`，确认"听到的就是这一项" |
| **设为基准层** | 原"潜行右键门"的功能，搬到面板里当按钮；再点一次取消（回到"最低层 = 1 层"的默认编号） |

- 音色取自**轿厢停靠的那扇门**，不是轿厢本身——轿厢会跑遍所有楼层，而提示音是每扇门的装修属性。轿厢精确到站的当刻播这一站的设置；开关门本身**不再发声**。
- **默认音效**用的就是 `assets/easyelevator/sounds.json` 里已配置好的 `easyelevator:elevator_arrival`（音频默认是 `sounds/man.ogg`），因此用资源包替换这个 ID 就能一次性改掉所有"默认"的门。
- **自定义文件**由模组写成一个运行时资源包（`resourcepacks/easyelevator_custom/`）并自动启用；权威副本存在 `config/easyelevator/arrival_sounds/`（`arrival_<槽>.ogg`），删掉资源包目录也能自动重建。每扇上传过音频的门占一个"门槽"（最多 64 个），槽位由门坐标推导，因此不需要额外存档字段。
- **全服同步**：设置在服务端（存在门的方块实体里，随区块存档）。同一个人改完，服务端立刻把最新设置推给附近所有玩家；上传的音频内容也会分发给站点附近的客户端，各自落到本机副本并重建资源包；**在音频上传之后才进服的玩家**，会在进服第一刻向服务端索取现有的全部自定义音频并补齐。因此专用服务器上**不需要**另外托管资源包 URL，装模组即可全服一致。
- **资源包只在音频真的变了时才重载**：模组会先比对内容指纹，一致就什么都不做。所以"每次进存档都闪一下红色 Mojang 加载画面"是不会发生的——只有你上传/换掉音频那一下才会重载一次。
- 一次上传后**自动的那次试听有可能没声音**（客户端此刻还在重载资源包，几百毫秒的窗口）；此后到站一定正常。要立刻确认音色，上传完成后再点一次「试听」即可。
- 把 `.ogg` **手工**放进 `config/easyelevator/arrival_sounds/`（命名 `arrival_<槽>.ogg`）也能生效：客户端进服时会把它投影成资源包并加载，适合服务器统一预置音效。
- **怎么上传**：打开面板后把 `.ogg` **直接拖进游戏窗口**（面板上会写着这句提示）。这是主要方式，不弹任何对话框、不依赖 AWT，路径带中文或空格也没问题。`选择文件…` 按钮是备用入口，靠 JDK 的 AWT 文件对话框；若这个游戏进程被启动器设成了 headless（`-Djava.awt.headless=true`），它会尝试改走系统原生对话框，两条路都不通时按钮会提示改用拖拽。启动日志里有一行 `File dialog backend: AWT` 或 `File dialog backend: native (AWT is headless)` 可看出走哪条路；拖拽启用成功则记 `Drag-and-drop uploads enabled (window handle …)`。
- 面板打开时**不暂停游戏**，与厅外呼叫面板、选站面板一致。

### 四种轿厢

| 型号（物品／实体 ID） | 速度 | 限载 | 外观 | 与普通型的差别 |
| --- | --- | --- | --- | --- |
| 电梯轿厢 `easyelevator:cabin` | 4 格/秒 | 不限 | 拉丝不锈钢内舱：深色踢脚线、不锈钢扶手、顶棚灯槽与自发光顶灯、金属门槛、操纵面板 | 默认型号；旧存档里的轿厢就是它 |
| 高速电梯轿厢 `easyelevator:high_speed_cabin` | **10 格/秒**（2.5 倍） | 不限 | **与世界里的普通型逐面相同**（只有物品图标是金色带速度标记） | 速度与加/减速段：巡航更快、加/减速各 8.0 格（普通型 3.2 格）；门时序、到站精度、防夹与联锁一个字都没改 |
| 观光电梯轿厢 `easyelevator:observation_cabin` | 4 格/秒 | 不限 | 四面墙改玻璃并加**分格窗**（上下压条 + 中梃 + 竖向分格），保留**四个支撑边**（角柱）、地板、顶板、扶手、顶灯与操纵面板 | 只有外观：碰撞、井道、载客、防夹与联锁与普通型逐条相同 |
| 强力电梯轿厢 `easyelevator:powerful_cabin` | 4 格/秒 | **20 人** | 外壳与门**与普通型逐面相同**，内饰换成重载套装：**双道扶手**、后壁两根立柱、门口一侧**第二块顶灯**、后壁**载重铭牌**（红字写出限载人数）、门槛内侧**防滑钢踏板**；物品图标是红色负载板 | 只有"能装多少人"：超过 20 人时进入**超载**（门保持全开、不派发行程，显示"超载"），人走出去即恢复。井道、碰撞、门时序与普通型逐位相同 |

- 四者的井道要求都是 **3×3×3**、都占 3 格高、都掉回**本型号**物品（空手潜行右键回收），因此换型号不需要改建井道或楼层门。
- 四者都走同一条 **S 形速度曲线**：参数由 `ElevatorParameters.CRUISE_RAMP_TICKS`（32 刻 = 1.6 秒，从静止加到本型号巡航速度所需的时间）与巡航速度解出——加/减速段各 1.6 秒，**普通／观光／强力各走 3.2 格、高速各走 8.0 格**，加速度峰值分别为 1.22 与 3.05 m/s²。想让启停更绵或更干脆，只改这一个常量（它同时决定段长、距离与加速度峰值）。
- 高速型按 **2.5 倍**步长运行（0.50 格/刻），单刻位移仍小于 1 格，所以整格站点不会被跳过，最后一步照旧精确吸附到站点高度；开关门与开门停留时间**不会**同比缩短，速度快只体现在运行段。
- **限载与超载**：限载人数在实体构造时注入（普通／高速／观光是 `ElevatorParameters.PASSENGER_NUM_LIMIT = 0`，即**不限载**；强力型是 `HIGH_PASSENGER_NUM_LIMIT = 20`）。**只有限载人数为正才会判超载**，所以把 0 改成别的正数，普通型号也能获得同样的保护。计数只数**玩家**（召唤动物不触发）；超载期间门一直是全开的，乘客可以自由进出，直到人数降到限载以下才恢复派发行程（恢复后重新计满 2 秒停留）。载重铭牌上的数字直接取自这个常量，**改数字不需要动任何贴图或几何**。
- 观光型的玻璃是**纯客户端绘制**：四个角柱、地板、顶板、压条、中梃和操纵面板保持不透明；侧墙、后墙及两扇铁框玻璃门使用原版无色玻璃。每片玻璃为零厚度双面，正反法线相反，按朝向剔除；透明像素不写颜色或深度，不会整片遮挡后绘制的楼层门。碰撞仍按 0.2 格厚实心墙生成，井道与站点尺寸不变。
- 强力型的重载内饰同样是**纯客户端绘制**，而且是在普通内饰表之上叠加的：`CabinRenderer.POWERFUL_PARTS` = 普通内饰前 12 行 + 10 行重载件 + 与普通型逐字相同的操纵面板 6 行。因此"看得见的强化件"不参与碰撞——井道、门口防夹与门联锁与普通型完全一致。
- 内饰的几何全部写在 `CabinRenderer` 的三张数据表里（`STANDARD_PARTS` / `POWERFUL_PARTS` / `OBSERVATION_PARTS`，每行 = 坐标 + 材质格号 + 是否自发光），改内饰就是改那张表；三张表的最后 6 行（操纵面板）必须逐字相同，因为观光舱与强力舱同样要显示层号与呼梯键；`POWERFUL_PARTS` 的前 12 行必须与 `STANDARD_PARTS` 的前 12 行逐字相同（"保留原来样貌"）。`python tools/generate_art.py` 会解析这三张表并校验"不越界 / 不留共面 / 格号合法 / 面板三舱一致 / 强力舱保留普通内饰且至少多出一件"。
- **灯光集中在舱内**：外壳、玻璃和导靴保持环境光；`CabinLighting.surface` 根据面中心、法线和灯位给朝向灯具的舱内表面补光，随距离衰减，上限 13 级。灯罩只有朝下的面使用 15 级方块光，侧边和背面保持环境光；天光分量不变，不修改世界光照或存档。**强力舱有两盏顶灯，因此它的舱内与外壳内面改走 `CabinLighting.surfaceTwoLamps`**（取两盏灯里更亮的一盏，而不是相加，上限仍是 13 级），门口一带因此比普通舱更亮；另外三种型号仍然只按舱顶后侧那一盏灯补光，观感与 2.2.0 逐像素相同。
- 整舱只用一张 4×4 的**材质图集** `textures/entity/cabin.png`，`CabinRenderer.Mat` 的枚举顺序就是格号；换配色只改 PNG，不用碰代码。强力舱与普通舱共用这张图集（重载件用的还是亮钢、扶手、灯罩、铭牌那几格），只有**物品图标**额外用一张红色负载板 `blank_powerful.png`。
- **玻璃使用原版透明材质**：`GlassLayers` 绑定 `minecraft:textures/block/glass.png`，顶点色统一 `0xFFFFFFFF`，通过原版 cutout 管线丢弃透明像素。世界玻璃不再使用有色图集格或低 alpha 覆盖层；`blank_glass.png` 仅用于物品图标。资源包可替换原版玻璃贴图，相关接口见 [材质说明](docs/ASSET_INTEGRATION.md)。
- 实现上四种轿厢继承同一个父类：`entity/AbstractCabinEntity` 承载全部逻辑，`CabinEntity` / `HighSpeedCabinEntity` / `ObservationCabinEntity` / `PowerfulCabinEntity` 每个只有十几行（构造时传入速度与限载人数、覆写回收物品、是否玻璃、是否重载内饰）。
- 高速型**外观与普通型完全一致**（同一个渲染分支、同一套几何），因此没法"看外观认速度"——只能从到站时间察觉。

### 一个具体示例

轨道放在 `(0, 64..80, 0)`，全部朝 `south`。在 `(0,64,3)`、`(0,72,3)`、`(0,80,3)` 放置楼层门底部中心，方向由轨道自动确定。

右键 Y=64 的轨道生成轿厢后，轿厢中心为 `(0.5,64,2.5)`，占地为 X=-1..1、Z=1..3，门朝南，门外走廊在 Z≥4。地板表面是 Y=64.2；楼层走廊表面可用 Y=64，0.2 格的门槛可正常走上。其他楼层同理。

每扇门占 X=-1..1、Z=3、Y=楼层高度..高度+2，门面位于这些方块朝走廊一侧，与轿厢正面的门口对齐。轨道 (0,64,0) → 轿厢中心 (0.5,64,2.5) → 门底部中心块 (0,64,3) → 走廊 Z≥4。

轿厢正面的模型和碰撞已内收0.2格，楼层门与轿厢门之间留有0.0125格间隙，避免门和门框重叠闪烁。上述轨道、楼层门位置和井道预留空间仍适用。

当前是**直上直下轨道**，横向相邻轨道是独立线路，不支持转弯、斜轨或分岔。每条线路同一高度只能设置一扇正面的门。

### 从旧版升级

原按钮的注册 ID `easyelevator:call_button` 保留，但现在显示并放置为「电梯门」，已有物品不会丢失。**已放置的旧按钮需拆下，按距轨道3格的新位置重放**；不自动覆盖周围建筑生成大门。旧按钮位置不再是有效站点。门的9个组成方块只计为一个站点。

已有存档里的轿厢不需要重建：它就是**普通电梯轿厢**（注册 ID 与行为都没变）。新增的高速／观光／强力轿厢是三件新物品（合成或用创造物品栏取出），各自的实体 ID 也是新的，因此不会与旧存档里的实体冲突；同一条线路上仍然只能有一台轿厢（四种型号一起计数）。

### 行为

- 普通与观光、强力轿厢速度 **4 格/秒**，高速轿厢 **10 格/秒**（2.5 倍）；开关门各 1 秒，开门停留至少 2 秒，停留到点**一律关门**，然后关着门停在本层待命。提高速度只缩短运行段，不会缩短开关门与停留时间。
- **超载（仅强力型）**：厢内玩家数超过限载（20 人）时，门**保持全开**、不派发行程；轿厢内模拟面板的第二行（平时显示层号的位置）与选站面板右上角的状态行都改显示「超载」。有人走出去就立刻恢复——回到开门状态、停留时间重新计满 2 秒。正在关门时发现超载会先把门重新打开（与防夹同一套反向动作）。超载**不是故障**：不会触发"检查轨道或障碍"提示，门一直开着让人能走出去。
- 楼层门与轿厢门是同一套动画：门框常驻，两扇门扇随进度向两侧收拢滑入门框，不再瞬间变成一堵墙。
- 楼层门门扇的贴图**跟着门板走**（不是被压扁，也不是被截断）：每扇只取"此刻还露在外面"的那一段贴图。哪一端拿哪一号纹理坐标只由"哪一扇"决定，**与朝向无关**——`BoxMesh` 的 u0 落在每个面的第一个顶点上，而 `doorBox` 的朝向镜像正好把四种朝向的差异抵消掉了（1.5.6 实机反馈"四个朝向只有一个门贴图是对的"就是按朝向翻端造成的）。
- **轿厢门是两扇对开滑门，与楼层门同一套机制**：门洞就是整个轿厢正面（内净宽 2.6 格），两扇外缘固定在侧壁内侧、先导端随进度向两侧移开，**全开时门洞全通**（净开度 2.598 格，玩家随便走）。门扇可见宽度会随开门变小（"盒子越收越窄"），这是 3×3×3 轿厢里的必然结果——门扇要整块平移出去又不许捅出车外，就得有 1.3 格深的门袋，而侧壁只有 0.2 格；楼层门也是这套机制，画面上读起来就是"门滑进门框"，里外两道门因此看起来一致。门扇贴图按"还露在外面"的那一段取，折边亮线会跟着先导端往外走。门板布局由纯算术类 `logic/SlidingDoor` 给出，渲染与碰撞取同一份数据。
- 到站误差容限 1e-7 格，最后一步精确对齐站点；运动样本是**绝对 double**（服务端每刻发、停车后补发 4 刻），客户端在前后两次提交位置之间逐帧插值；**2.2.0 起不再单独锁定镜头**，也没有额外的显示延迟缓冲——渲染、碰撞与乘客共用同一组样本。
- 请求按**运行方向上的位置顺序**停靠（不是按键先后）：同一方向上的楼层依次服务，相同站点重复请求合并；厅外呼叫按方向只被顺路的那一趟接走，反方向的孤立呼叫也会被服务（空车去接）。轿厢内选站与厅外呼叫各自最多等待 128 条。
- 门未完全关闭不能移动；门口有生物会重新开门并保留原请求。
- 乘客站在空心轿厢内随轿厢移动，不要求骑乘；服务端同步位置并清除下落伤害。
- 断轨、轨道朝向不一致、运行区域有实体/方块障碍、区块未加载时停止；恢复后继续原行程。
- 运行中拆除目的站电梯门会暂停并取消该目的站；其他有效请求可以继续，或从轿厢重新选站。避免在半空开门。
- 轿厢、目标、队列和门进度保存进世界。重载后先检查线路再恢复运行。
- 不主动加载区块；线路及井道需要在已加载范围内。多人服务器和客户端都要安装模组与 Fabric API。

## 替换模型与音效

详细接口见 [docs/ASSET_INTEGRATION.md](docs/ASSET_INTEGRATION.md)。

- 轨道模型：`assets/easyelevator/models/block/elevator_rail.json`
- 楼层门**门框**模型（常驻）：`assets/easyelevator/models/block/landing_door_frame_*.json`（底行另有 `*_bottom` 三件，带底座与门槛）；门物品图标：同目录 `call_button.json`
- 楼层门**门扇**：`src/client/java/org/DJB/easyelevator/client/LandingDoorRenderer.java`，几何在 `block/LandingDoorGeometry.java`
- 轿厢及双扇门：`src/client/java/org/DJB/easyelevator/client/CabinRenderer.java`（普通与高速型共用同一套不透明外壳与内饰；强力型在普通内饰之上叠加"重载"件 `POWERFUL_PARTS`；观光型另走 `drawObservationShell` + `drawObservationGlass`，玻璃材质见 `GlassLayers`，局部照明见 `logic/CabinLighting`）
- 铁框玻璃门（观光轿厢的门、以及观光线路上的楼层门）：`client/FramedGlassDoor.java`（画铁框 + 中间的零厚度玻璃面），边框/玻璃的尺寸由纯算术类 `logic/FramedLeaf.java` 给出；玻璃层见 `client/GlassLayers.java`
- **线路级的门样式**：楼层门是不是玻璃门由"这条线路上那辆轿厢是不是观光型号"决定（`LandingDoorBlockEntity.glassDoors()`，每刻缓存一次，判据是轿厢的 `glassWalls()`）。所以观光轿厢所在轨道上的**每一层**楼层门都会变成铁框玻璃门，换回普通轿厢又变回钢门。
- 轿厢材质图集：`assets/easyelevator/textures/entity/cabin.png`（4×4 共 16 格，格号见 `CabinRenderer.Mat`）
- 方块贴图：`assets/easyelevator/textures/block/`（`blank` 门框/轨道亮钢、`blank_door` 亮钢门扇、`blank_plate` 机加工深色板、`blank_screen` 门楣凹进去的显示屏、`blank_speed` 高速图标金板、`blank_powerful` 强力图标红色负载板、`blank_glass` 观光图标玻璃）
- 运行/到站音效：`assets/easyelevator/sounds.json`（只有 `elevator_running` / `elevator_arrival` / `elevator_arrival_custom` 三项；**开关门不再发声**。`elevator_arrival` 是每个门设置面板里"默认音效"那一项的来源，`elevator_arrival_custom` 只是字幕占位，音频由上传填充）
- **每扇门的到站音效设置**：面板 `client/DoorSoundScreen.java`，目录与选项表 `logic/DoorSounds.java`，单门设置 `logic/DoorArrivalSound.java`，音频落盘 `logic/DoorSoundPersistence.java`，运行时资源包 `client/DoorSoundPack.java`
- 轿厢背面另有**抱轨导靴**（`CabinRenderer.drawGuideShoes`，纯渲染、不进碰撞），上下各一组夹住轨道，于是轿厢看上去是骑在轨道上运行的。
- 门动画：轿厢门 `AbstractCabinEntity.doorProgress(tickDelta)`；楼层门门扇 `LandingDoorBlockEntity.openProgress(tickDelta)`，逐刻等于在站轿厢的门进度，0 关闭、1 打开。
- 服务端扩展事件：`ElevatorEvents.PHASE_CHANGED`、`ElevatorEvents.ARRIVED`。

模型与贴图不是手改的，而是由两个脚本生成（都是纯 Python 3、无第三方依赖、可重复运行且输出逐字节一致）：

```powershell
python tools/generate_art.py    # 方块/物品模型 + 全部贴图 + 几何校验
python tools/generate_data.py   # 方块状态、本地化、配方、掉落表、音效钩子
```

`generate_art.py` 同时是模型与内饰的一致性检查：它会校验门框模型与 `LandingDoorGeometry` 的尺寸一致、物品模型不越出 16 格方块盒，以及轿厢内饰表的三条不变量（不越界 / 不留共面 / 格号合法）。改完模型或内饰表请先跑它。

## 构建

先将 `JAVA_HOME` 指向 **JDK 21**，然后在项目目录执行：

```powershell
.\gradlew.bat build
```

成品在 `build/libs/easyelevator-2.2.1.jar`；带 `-sources` 后缀的是源码包，不放入 mods 文件夹。

完整说明见 [工程构建与打包说明书](docs/BUILD_AND_PACKAGING.md)；所有运行、精度、动画、尺寸、面板和音效参数见 [电梯参数手册](docs/PARAMETERS.md)。

本机快捷构建和两种打包（把 `<JDK21>` 换成你自己机器上的 JDK 21 目录；省略 `-Jdk` 时脚本回退到 `JAVA_HOME` 与 PATH）：

```powershell
.\tools\build.ps1 -Jdk '<JDK21>' -Task build
.\tools\build.ps1 -Jdk '<JDK21>' -Task packageRelease
.\tools\build.ps1 -Jdk '<JDK21>' -Task packageProject
```

开发启动：`./gradlew.bat runClient`。

工程内**没有常驻自动化测试**，日常验收方式见 [人工验收清单](docs/TESTING.md)（需要真人进游戏逐项确认）。另有一套**可选开启**的乘客回归测试（`src/gametest`：12 个 `@GameTest` + 1 个客户端冒烟测试），加 `-PriderTests` 才会构建，永远不会进发行包：

```powershell
.\tools\build.ps1 -Jdk '<JDK21>' -Task runGameTest
.\tools\build.ps1 -Jdk '<JDK21>' -Task runRiderClient
```

## 文件组织

| 目录/类 | 职责 |
| --- | --- |
| `block/`、`item/` | 轨道、3×3楼层门及呼叫联锁、轿厢放置和回收 |
| `logic/ElevatorLine` | 轨道连续性、站点扫描、单线路单轿厢 |
| `logic/ElevatorController` | 独立状态机、门联锁、请求队列、集选调度 |
| `logic/MotionProfile` | S 形速度曲线（纯 Java）：由巡航速度与 `CRUISE_RAMP_TICKS` 解出加速度/jerk 上限，按时间求值给出每刻位移 |
| `entity/AbstractCabinEntity` | 四种轿厢的共同父类：实际位移、乘客、限载与超载判定、障碍检测、存档、同步 |
| `entity/CabinEntity`、`HighSpeedCabinEntity`、`ObservationCabinEntity`、`PowerfulCabinEntity` | 普通／高速（2.5 倍速）／观光（玻璃墙）／强力（限载 20 人 + 重载内饰）四个型号，各自只声明速度、限载、回收物品与外观开关 |
| `network/RiderMove`、`logic/RiderMotionHistory`、`client/CabinMotion` | 2.2.0 乘客随厢移动：客户端只认绝对样本、把所用样本编号塞进移动包；服务端按自己的历史高度补偿网络延迟后再交给原版校验 |
| `mixin/EntityViewMixin` | 空心轿厢地板、侧壁、门的实体碰撞 |
| `mixin/client/CabinCrosshairMixin` | 轿厢内准星裁决：乘客点哪都开面板；门全开时允许射线从门洞穿出去打外面的方块 |
| `mixin/client/ClientPlayerEntityMixin` | 在玩家物理更新前推进轿厢与乘客；把原版移动包换成携带轿厢样本编号的 `RiderMove` |
| `network/` | 面板数据和选站请求；服务端验证 |
| `client/` | 面板、轿厢外壳与内饰、位置音效循环 |
| `client/ElevatorScreen`、`logic/PanelLayout` | 轿厢内选站面板（网格 / 翻页 / 开关门）与它的纯算术网格分页 |
| `block/LandingDoorGeometry`、`logic/SlidingDoor`、`logic/FramedLeaf`、`logic/LeafUv` | 门几何的**单一数据源**（渲染与碰撞同源）：楼层门门扇 / 轿厢两扇对开滑门 / 铁框玻璃门布局 / "贴图随门滑动"的 UV 区间 |
| `logic/CabinLighting` | 舱内表面补光、灯罩朝下发亮、外表面环境光 |
| `client/GlassLayers` | 原版无色玻璃贴图与 cutout 渲染层 |
| `client/CabinRenderer` | 轿厢外壳 / 内饰数据表（普通、强力、观光三张）/ 观光分格玻璃 / 材质图集与 UV 分格 / 轿内面板文字与载重铭牌红字 |
| `client/BoxMesh` | 长方体与零厚度单面的共用绘制工具，支持按 UV 矩形取图集分格 |
| `client/LandingDoorScreen` | 楼层门上的厅外呼叫面板（▲ / ▼ / 关闭 三个按钮竖排，呼叫未完成时按钮标红） |
| `client/DoorSoundScreen` | 楼层门的专属设置面板（潜行右键打开：到站音效开关、音效选择/上传/试听、设为基准层） |
| `logic/DoorSounds` | 到站音效目录：默认/自定义/预设原版音效的选项表，以及"选项 + 门槽 ↔ 音效事件 ID / 音频文件名"的换算 |
| `logic/DoorArrivalSound` | 单扇门的到站音效设置（不可变值对象，读写方块实体 NBT） |
| `logic/DoorSoundPersistence` | 上传音频的权威副本存储（`config/easyelevator/arrival_sounds/`），服务端与客户端共用 |
| `client/DoorSoundPack` | 把权威副本投影成运行时资源包 `resourcepacks/easyelevator_custom/`；带内容指纹，只在真的变了时才重载资源 |
| `client/FilePicker`、`client/FileDropHandler` | 上传本地 `.ogg` 的两条入口：AWT 系统对话框（或 headless 下的原生兜底）与**拖拽入窗**（主要方式） |
| `client/StatusArrow` | 闪烁的上行/下行箭头字符，门框顶部与轿厢内面板由它同相驱动 |
| `logic/FloorIndicator` | 楼层编号：基准层 = 1 层，其上 2、3…，其下 B1、B2…（轿厢面板 / 门框 / 选站面板三处共用） |
| `api/` | 到站和状态变化扩展事件 |

游戏内验收步骤见 [docs/TESTING.md](docs/TESTING.md)。

接手开发请先读 [项目开发手册](docs/PROJECT_MANUAL.md)：架构分层、文件引用关系、函数调用关系、关键类与关键函数、对外接口与扩展指南。
