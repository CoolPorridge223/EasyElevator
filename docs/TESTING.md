### 开门键改为"中断关门"（2026-10-02）

- **玩家报告的 bug**：门正在关闭时按开门，门继续关，而且**本层被排进了呼叫队列**，于是电梯开走之后还要回来一趟。根因是旧实现把"开门"当成"呼叫本层"来做——直接调用 `requestStop(本层)`，既没有反向门动作、又真的入了一次队。
- **修法**：开门键改成纯门操作，调用 `ElevatorController.forceOpen()`（它在 CLOSING 时切回 OPENING、在门已全关但停在本层时直接开门，并且**完全不碰 target/queue**），受理条件与面板按钮一致：`status()==IDLE` 且车体精确停在某站点（`CabinEntity.doorCommand`）。这样"开门"= 中断关门／重新开门／延长停留，永远不会产生新的呼叫。
- 自动检查：GameTest 新增 `openButtonInterruptsClosing`（等门关到一半再按开门，断言呼叫计划仍然只有原来那一个目的站、下一刻相位变成开门、门在本层重新开到全开、原来那趟行程照常完成且没有多余请求留存），现在共 **12/12** 通过；`ElevatorControllerTest` 也补了一条"反向开门不改 target/queue"的断言。`./gradlew.bat build` 与四套纯 Java 测试全部通过。

### 运行途中保存退出后乘客掉出电梯（2026-10-02）

- **玩家报告的 bug**：人物在轿厢里、电梯正在运行时"保存并退出"，下次进入游戏人物会掉出电梯。
- **根因（两类实体的载入时机差）**：轿厢是区块实体，随区块一起载入；玩家实体由登录流程单独载入，**必然晚于区块实体**。存档里的行程在载入第一刻就会被状态机的 MOVING→BLOCKED 分支恢复（门是关的、目的站还在），于是轿厢抢在玩家实体出现之前开走；玩家随后被放回自己的存档坐标——已经空掉的井道——脚下没有地板，直接掉出电梯。第二条同源路径是客户端首帧还没有轿厢实体（空心碰撞由 `EntityViewMixin` 注入），本地玩家先自由落体一段，而服务端跟随客户端上报的位置，于是相对高度跌破 `containsPassenger` 的 0.14 格下沿，轿厢不再认他是乘客、也就不会再带着他走。
- **修法（乘客名册 + 先重验再继续）**：轿厢每刻记录"站在厢内的玩家"的 UUID 与**相对轿厢底部中心的偏移**，随实体 NBT 的 `Riders` 一起存档（相对量，因此读档后轿厢停在别处也仍然有效）。读档时若名册非空，就先保持静止等这些人回到世界（`RIDER_WAIT_TICKS` = 600 刻 = 30 秒封顶，避免乘客永不回来时把电梯钉死）：等待期间谁在井道里出现，就按名册偏移放回厢内——复用运行时载客那条 `requestTeleport` 通路（服务端坐标立刻生效、保留视角），同时清掉下落距离与纵向速度，因此不会结算摔落伤害。名册齐了、等待窗口用尽、或车上已经有别的乘客要走，就立刻放行继续原行程；阻塞仍然走 BLOCKED，所以**行程、队列、门联锁语义一个字都没变**。
- **名册维护规则**：门已全开（`DOOR ≈ 1`）时仍在线上却不在厢内的玩家属于正常离开（开门本来就是让人走），从名册划掉；**掉线的玩家一律保留**——他们没有能力自己走出轿厢，只可能是被行程丢下的人（掉线重进、客户端首帧掉下去、读档还没归位都属于这一类）。找回只在"同一条井道"里进行：世界全高、水平 ±2 格查询，再要求水平落在轿厢内缘 ±1.31 格内，与 `containsPassenger` 共用同一条水平判据（`insideFootprint`）；站在楼层门口或走廊上的玩家横向就已经在内缘之外（门槛在本地 Z=1.3..1.5 格），不会被误拽进轿厢。
- 自动检查：GameTest 新增 `loadedCabinWaitsForItsPassenger`（运行途中写 NBT → 丢弃原实体 → 用同一份 NBT 生成一辆新轿厢 → 乘客暂时离开井道，等价于"保存退出再进入"；断言读档后 15 刻内一步都没走且目的站仍在、乘客回到井道后被放回厢内地板并随厢继续上行、最后精确到站开门），服务端 GameTest **13/13 通过**；把"等待乘客"临时改成直接放行后，该用例立刻在 `Loaded cabin must not move before its passenger is back` 处失败（12/13），确认它钉住的正是这个 bug。四套纯 Java 测试（`tools/test-logic.ps1` 的等价命令）全部通过；`javac --release 21` 对 main/client/gametest 三个源集全量编译无错误。
- 仍待人工确认：真人"运行途中保存退出 → 再次进入"必须仍站在轿厢里并接着走完原行程；多人时一人掉线重进也应回到厢内；读档后 30 秒内没有人回来时行程照常继续（不会把电梯永久钉在某层之间）。

- **观光轿厢渲染崩溃修复（放置即崩溃 → 已修）**：第一版观光渲染在"取了半透明玻璃层"之后又回头往不透明层写舱内操作面板，触发客户端 `java.lang.IllegalStateException: Not building!`（渲染中崩溃，游戏随即保存退出）。根因是原版 `VertexConsumerProvider.Immediate` **每层只有一个正在构建的缓冲**：通过 `getBuffer` 切到另一层时上一层会被结束并提交，先前拿到的 `VertexConsumer` 立即失效，继续写顶点就抛这条异常。修法是把 `CabinRenderer.render` 固定成"按层分组、画完不回头"：① 不透明层（外壳 + 操作面板）→ ② 文字层（面板红字）→ ③ 半透明层（玻璃墙与玻璃门，仅观光型号，必须最后画）。约束已写进 `CabinRenderer` 的类注释，`LandingDoorRenderer`（先文字、后门扇层）本来遵守同一条约定。
- **观光玻璃"剔除楼层门"与"衔接处闪烁"修复（实机反馈 → 已修）**：实机发现两处表现问题。
  ① **看不见每层的电梯门**：原版世界渲染顺序是**实体 → 方块实体**（`WorldRenderer.render` 里 "entities" 早于 "blockentities"），而原版 `entity_translucent` 层默认写深度（写掩码 `ALL_MASK`）；观光轿厢的玻璃比楼层门更靠近观察者，它一写深度，之后才由 `LandingDoorRenderer` 绘制的门扇就被深度测试整片剔掉。修法是自建渲染层 `CabinRenderer.GLASS_LAYER`（`easyelevator_cabin_glass`）：照抄 `entity_translucent` 的着色器、贴图、混合与"禁止剔除"，只把写掩码改成 `RenderPhase.COLOR_MASK`（只写颜色、不写深度）——与原版对方块半透明层（玻璃、水）的处理一致，玻璃不再遮挡任何后画几何，自身仍受深度测试约束（会被舱体不透明件正确遮挡）。
  ② **玻璃门与不透明框架衔接处轻微闪烁**：玻璃原本是 0.12 格厚的薄板，其端面与角柱内面、上下两面与地板/顶板恰好共面，浮点深度差让两个面在镜头移动时来回抢先。修法是改为**零厚度单面**（新增 `BoxMesh.planeX/planeY/planeZ`，单面必须画在禁止剔除的层上才正反都可见），并把四周尺寸内缩 0.01 格（侧墙贴墙心 X=∓1.4、后墙 Z=-1.4、门扇 Z=正面-0.01，Y=0.21..2.79）。单面还顺带修掉了"薄板正反各叠一次导致整舱发灰"的问题：现在每层玻璃只叠一次，隔着轿厢看穿两面约 44%。
  碰撞未改动（仍取 `collisionBoxes()` 的 0.2 格实心墙），因此井道、载客、防夹与联锁与普通轿厢逐位相同。这两处都是纯客户端绘制，无法用无头 GameTest 覆盖，需在客户端确认。
- **客户端 smoke UI 测试已按要求移除**：删除了 `ElevatorClientSmoke`、`build.gradle` 里的 `clientSmoke` 运行配置、测试模组 `fabric.mod.json` 的 `client` 入口与对应的 IDEA 运行配置。因此本项目不再有"启动客户端并截选站面板图"的自动检查，玻璃观感、10 格/秒乘坐手感等只能由下面的人工步骤确认。
- **仍待人工确认**：① 观光车玻璃的通透度与观感（`CabinRenderer.GLASS_COLOR` / `GLASS_DOOR_COLOR`）、四个角柱与地板顶板的不透明对比，以及"厢内朝外看"与"走廊朝厢内看"两个方向是否都自然；② 高速车的实际乘坐体验（10 格/秒时相机平滑与乘客跟随；每刻样本间隔 0.5 格，远小于 `MOTION_SNAP_DISTANCE` = 4 格，理论上不会触发位置吸附）；③ 物品栏里三个图标（白 / 淡金 / 淡蓝）是否足以区分型号；④ 在同一条线路上换用另一种型号（同线路只允许一台轿厢，三种型号一起计数，因此必须先回收旧车）。

以下是仍需要游戏客户端及多人环境观察的验收步骤，不能用自动测试通过代替玩家实际乘坐验证。

1. 用 README 示例搭建三个站点；面板应恰好显示三个方形按键，编号从左到右为 3 2 1（最底层 1 层在右下角），右键每扇楼层门可以叫回轿厢；再往上加几个站点，按键应重新排成尽量长方形并可用 `<` `>` 翻页。
2. 一扇3×3门只显示一个站点；拆任意一部分会移除整扇门并使站点减少。
3. 相邻另一列轨道加楼层门和第二轿厢：两条线路各自工作，站点不串线。
4. 同一连续线路放第二轿厢应被拒绝。先断开成两条线路各放一个，再接通，呼叫应提示多个轿厢。
5. 进入轿厢右键开面板，上行和下行；地板应支撑玩家，门关闭前不启动，到站开门后可走出。
6. A→C 运行时再呼叫 B：先到 C，再到 B。重复点同一目的站不应反复往返。
7. 关门时站在门口：重新开门，离开门口后继续关门和行程。门关闭后不能走出。
8. 运行路径放石块或拆轨：轿厢暂停且停止运行声音；恢复轨道/清障后继续。目的站拆除后不在半空开门，重新选有效站可恢复。
9. 保存退出，重新进入，检查当前位置、目标、队列和门状态；运动中的存档先重验再继续，并确认人物仍在轿厢里（读档后轿厢会先等存档时的乘客回到世界再继续，上限 `RIDER_WAIT_TICKS`）。
10. 两名玩家同时乘坐，反复上下行，检查是否跌落、卡墙、被服务端位置校正拉回，以及面板打开期间能否随车移动。
11. 从轿厢外发送选站请求、拆除楼层门后使用旧面板请求：服务端应拒绝无效站点及远程请求。
12. 换维度或离开区块再返回：没有重复轿厢、循环声音残留或额外物品。
13. 换入四段 OGG：运行期间循环，停止/故障立刻停声，到站一次、开关门分别一次；查看另一名玩家是否听到一致。
14. 调试四种朝向、世界高度边界、区块边界上的井道；未加载区域不应强制穿越。
15. 1.1.0 平滑专项：第一人称观察地板和门框，运行时转头、开面板；到站后立刻跳跃或离开，不应被旧的平滑镜头锁住。第三人称、低帧率和不同网络延迟分别检查。
16. 测量相隔8格的两个站点：只计门已关到开始开门之间的运行时间，正常20 TPS约2秒。微小余量不应反向抖动或停在楼层旁。
17. 四种朝向分别从走廊和轿厢内观察**关门、半开、全开**的门：开关门应像轿厢门一样连续滑动、与轿厢门同步，两扇门扇收进两侧门框而不是整面瞬间消失；门框（左右立柱与门楣）始终可见、比门扇亮，关闭时正中能看到一条细门缝；转动视角并上下运行经过楼层时门面、门框与上框应无重叠闪烁；同时确认内收后的门槛仍可正常进出。`cabinClearsLandingDoorInEveryDirection` 自动检查四种朝向、五个轿厢门进度和三个楼层门门扇位置下的几何间隙，`landingLeavesSlideIntoTheFrame` 自动检查门框常驻、门洞开合与中缝位置，实际画面仍需客户端观察。
18. **高速轿厢专项**：在普通轿厢运行的那条线路上换成高速轿厢（先空手潜行右键回收旧车）。同一段行程应明显更快（10 格/秒 ≈ 2.5 倍），但**开关门与门口停留时间不变**、到站仍精确停在楼层高度、运行中门保持关闭；第一人称上下各乘一次，检查相机平滑、无抖动、无"移动过快"回弹；再加一名乘客，确认两人都随厢移动且不摔伤。外观应与普通轿厢**看不出区别**（同一个渲染分支）。
19. **观光轿厢专项**：换成观光轿厢，从走廊朝厢内看、再从厢内朝外看：左右侧墙、后墙与两扇门应透光，四个角柱、地板与顶板仍不透明；进出门口、贴墙走动时**不应掉出轿厢**（玻璃墙仍是实心碰撞）；上楼、下楼过程中观察玻璃与角柱之间、玻璃与楼层门框之间应无共面闪烁；必要时按 `docs/ASSET_INTEGRATION.md` 调整 `CabinRenderer.GLASS_COLOR` / `GLASS_DOOR_COLOR` 的通透度。

20. **厅外呼叫面板**：右键任意一扇完整的楼层门 → 弹出竖排面板（▲ / ▼ / 关闭）。按 ▲ 后按钮应立刻变红并一直红着；轿厢到达本层开始开门的那一刻变回灰色（面板开着时同刻刷新，关掉再打开也应是灰色）。按 ▼ 同理。没有轿厢或同线路有多台轿厢时，按按钮应收到对应提示而不是静默失败。
21. **顺路与掉头**：车内按 8 层，然后分别在 5 层按"上行"、8 层按"下行"。预期：上行途中先停 5 层（接上行的人），到 8 层后门开（此时 8 层的下行呼叫仍应亮着，因为它要等轿厢掉头下行才被接走），轿厢到顶掉头下行时才熄灭 8 层的下行按钮。
22. **基准层与地下层编号**：在中间某层潜行右键一扇完整的门 → 该层显示 1。打开轿厢内面板：按钮编号应为 …… B2 B1 1 2 3 ……；停在各层时轿厢内面板与门框顶部的红字应显示 1 / 2 / B1 等（不再出现 0 或负数）。拆掉基准门后应回到"最底层 = 1 层"。

23. **顺路重排（运行途中插入）**：在轿厢里先按一个较远的楼层（例如 10 层），关门起步后走到 2~3 层时，让别人（或自己跑出去）在 5 层按"上行"。预期：轿厢在 5 层停下开门，5 层的按钮随即熄灭，然后继续前往 10 层——不再是直接开过 5 层。同样地，运行途中在轿厢面板里按 5 层也应先停 5 层。反方向的呼叫（车向上时按 5 层"下行"）不应让轿厢半路掉头，而是等它到顶掉头下行时才接。
24. **面板观感**：三个按钮应是同尺寸小方块（▲ / ▼ / ×），关闭键不再是一条长按钮；红/灰/悬停三态与原版长条按钮无关，缩放窗口后整列仍居中等宽。
