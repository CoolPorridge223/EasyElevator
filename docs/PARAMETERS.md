# EasyElevator 电梯参数手册

适用模组 **2.2.0**、Minecraft **1.21.1**、Fabric Loader **0.19.2**、Java **21**。

> 面向**调参与排查**：每个常量的数值、单位、派生公式与"改一处、跟着改"的联动清单。
> 姊妹文档：[项目开发手册](PROJECT_MANUAL.md)（架构、调用关系与接口）、[人工验收清单](TESTING.md)、
> [模型音效接口](ASSET_INTEGRATION.md)、[构建与打包](BUILD_AND_PACKAGING.md)、[README](../README.md)（玩家向）。

当前参数采用**源码常量**，不是游戏内设置，也不会自动生成 JSON 配置文件。修改后必须重新构建，并同时更新服务端和客户端。

## 1. 运行、精度和时序

主要入口：`src/main/java/org/DJB/easyelevator/logic/ElevatorParameters.java`。

| 参数 | 默认值 | 单位与作用 |
| --- | --- | --- |
| `TICKS_PER_SECOND` | 20 | 换算用的标准游戏 tick/s；不能通过改这个数改变 Minecraft 时钟 |
| `SPEED` | 0.20 | 格/tick，正常 20 TPS 时为 **4 格/秒**，是 1.0 的两倍；普通轿厢与观光轿厢的**巡航速度上限** |
| `HIGH_SPEED` | 0.50 | 格/tick，`SPEED × 2.5`，正常 20 TPS 时为 **10 格/秒**；只给高速轿厢用 |
| `CRUISE_RAMP_TICKS` | 32 | 刻，轿厢从静止加到**本型号巡航速度**所需的时间（1.6 秒）。S 形曲线的唯一舒适度旋钮：加/减速段时长 = 它，加速度峰值 = `巡航速度 / 它`，单段距离 = `巡航速度 × 它 / 2` 格 |
| `MAX_ACCELERATION` | 0.15 | 格/tick²，加速度**硬上限**（60 格/秒²），只在 `CRUISE_RAMP_TICKS` 被调得极小时才起作用；实际工作点由 `CRUISE_RAMP_TICKS` 推出：普通/观光 0.00625（≈1.22 m/s²）、高速 0.015625（≈3.05 m/s²） |
| `POSITION_EPSILON` | 0.0000001 | 格，同层判断和最后一步的浮点误差容限 |
| `DOOR_TICKS` | 20 | 单次开门或关门各 1 秒（三种轿厢共用，不随速度变化） |
| `DWELL_TICKS` | 40 | 门完全打开后的最短停留 2 秒；到点自动关门（**没有请求也关**，关着门停在本层待命） |
| `MAX_REQUESTS` | 128 | 轿厢选站与厅外呼叫各自的等待队列上限，不包含正在执行的目标 |
| `RIDER_WAIT_TICKS` | 600 | 刻，读档后等"存档时在车上的乘客"回到世界的上限（30 秒）；超时后行程照原计划继续 |

速度公式：`格/秒 = SPEED × 20`。例如 3 格/秒用 0.15，6 格/秒用 0.30。服务端低于 20 TPS 时实际运行时间会变长。不要为了“更细”而减小 SPEED，否则会直接降低速度。

速度不再是全局唯一值：`ElevatorController` 把巡航速度作为**实例字段**在构造时注入（`new ElevatorController(ElevatorParameters.HIGH_SPEED)`），因此普通 / 高速 / 观光三种轿厢共用同一个状态机实现、同一个队列与同一套门联锁，只有"每刻走多远"不同。约束有两条：① 巡航速度必须满足 `速度 + POSITION_EPSILON ≤ 1 格`，否则单刻可能跨过整格站点、到站吸附失效；② 改速度不会改变 `DOOR_TICKS` / `DWELL_TICKS`，所以"更快"只体现在运行段。非正数或非有限值会退化为 `SPEED`（坏存档不会把轿厢钉死）。

## 1.1 S 形速度曲线（Jerk-limited profile）

轿厢**不是**匀速运行：位移由 `logic/MotionProfile` 按时间参数化的 S 形曲线给出——启动缓慢加速、
中段匀速、到站前平滑减速。曲线满足三重上限：速度 ≤ 巡航上限、`|加速度| ≤ MAX_ACCELERATION`（硬上限）、
`|jerk| ≤ 2·a_p/T`。实际工作的加速度峰值与 jerk 不是常量，而是由**巡航速度与
`CRUISE_RAMP_TICKS`（T）解出**：`a_p = v / T`、`j = 2·a_p / T`，于是加/减速段恰好各 T 刻，
速度在这 T 刻里从 0 升到 v（加速度走一个等腰三角形，峰值 a_p）。整条曲线在"开始移动 / 运行途中改道"时
一次规划完成，之后每刻只按时间求值，因此没有逐刻累加误差，也不需要客户端外推。

| 现象 | 旧实现（每刻固定步长） | 现在（S 形曲线） |
| --- | --- | --- |
| 启动 | 第一刻直接 0.20 / 0.50 格，"一顿就起步" | 从 0 连续升上去；16 刻（0.8 s）升到加速度峰值，再过 16 刻到达巡航速度 |
| 到站 | 最后一刻从巡航速度直接归零 | 提前若干格开始平滑收速，最后一刻速度已经很低 |
| 短行程峰值 | 固定等于 `SPEED` | 由距离反解（可能低于巡航上限），近距离不会"猛冲一下再急停" |
| 长行程峰值 | `SPEED` | 恰好 `SPEED`，且巡航段与旧实现一样快 |
| 实际加速度峰值 | 无（速度突变） | 由 `v / CRUISE_RAMP_TICKS` 给出：普通/观光 0.00625 格/刻² ≈ 1.22 m/s²、高速 0.015625 ≈ 3.05 m/s²（真实电梯舒适区 1.0~1.6 m/s² 内） |
| 加/减速距离 | 无（瞬时启停） | 普通/观光各 **3.2 格**、高速各 **8.0 格**（= `速度 × T / 2`），比旧的 1.86 / 2.64 格明显拉长 |

调参口径：`CRUISE_RAMP_TICKS` 是**唯一**的舒适度旋钮——加/减速段的时长、距离与加速度峰值全部由它
与巡航速度推出，`MAX_ACCELERATION` 只是兜底硬上限（防止把 T 调得过小）。实测（普通车 / 高速车，纯运行时间）：

| 行程 | 普通车（4 格/秒） | 高速车（10 格/秒） |
| --- | --- | --- |
| 1 格 | 约 2.2 s | 约 1.6 s |
| 5 格 | 约 3.7 s | 约 2.7 s |
| 10 格 | 约 4.9 s | 约 3.5 s |
| 100 格 | 约 27.4 s | 约 12.4 s |

短行程里"平滑"占了主要时间（这正是舒适度的代价）；距离越长，S 段的固定开销占比越小，
高速车的巡航速度优势才体现出来——与真实高速梯一致。作为对照：把 `CRUISE_RAMP_TICKS` 改小到 24
（单段 2.4 格）能让 4 格行程从 3.45 s 回到约 2.6 s，加速度峰值升到 1.63 m/s²。

控制器最后一步直接使用站点 Y；没有“必须移动满 0.2 格才能动”的门槛。小于一步的剩余距离仍会移动，
不会来回越过楼层——只是这一小段会分摊到若干刻上（曲线减速），最终严格落在站点高度。
到站误差容限从旧版 1e-5 收紧为 1e-7；这不是显示帧率，也不是一个强制的最小位移。
位置与运动同步包使用 double，不把高度取整到格、0.1 格或小数两位。

以相差 8 格的楼层为例：普通车纯运行约 4.5 秒；再加等候、关门、开门时间。
提高速度不会同比缩短固定的门动画与等候时间。

建议保持 SPEED>0、MAX_ACCELERATION>0、CRUISE_RAMP_TICKS≥1、DOOR_TICKS≥1、DWELL_TICKS≥0、MAX_REQUESTS≥1。
过高速度需要重新验证乘客、障碍及客户端同步；调 `CRUISE_RAMP_TICKS` 会同时改变"舒适度"和每趟耗时
（它与加/减速段时长成正比、与加速度峰值成反比），改完请进游戏按
[人工验收清单](TESTING.md) 的乘坐类条目确认手感，并核对启停看起来仍然平滑。

## 2. 平滑显示与网络

正常运行的 `motion_frame` 仍由服务端每刻发送，停车后补发 4 刻。客户端在本地玩家 tick 之前（`client/CabinMotion.beginPlayerTick`）统一提交轿厢位置与乘客位移，渲染在前后两刻物理位置之间插值（`CabinMotion.renderY`）。不另设相机高度锁定，也不预测尚未收到的电梯行程。其他玩家的渲染仍使用原版同步。

`rider_move` 将原版移动包与本地采用的服务端样本编号一起发送。服务端校验轿厢身份、乘客位置与样本时效，使用自身历史记录计算 `当前轿厢Y + (客户端玩家Y - 样本轿厢Y)`，然后交给原版网络处理器做速度、碰撞和传送确认检查。乘客自己的 X/Z、视角、跳跃与落地标志保留。正常承托不会发送传送包，也不会清零速度或强制落地；真实传送尚未确认时不承托。

| 参数 | 默认值 | 意义 |
| --- | --- | --- |
| `RiderMotionHistory.MAX_AGE` | 60 tick | 服务端承认的历史样本最大时效，记录最多 61 个样本；过期或未知编号不给位移补偿 |
| `MOTION_STALE_TICKS` | 10 tick | 客户端长期未收到位置包时停止乘客绑定 |
| `MOTION_SNAP_DISTANCE` | 4.0 格 | 轿厢本刻位移超过此值时视为**传送/归位**而不是平台运动：该刻不再托举乘客（否则会把乘客一起拽走、甩出轿厢）。轿厢本体位置照旧提交 |
| `MOTION_SETTLE_TICKS` | 4 tick | 停车后补帧，含最后一次精确到站的位置 |

客户端**不使用额外的视觉延迟缓冲**（旧的两刻插值缓冲已随 `MotionTimeline` 一并删除），以免可见地板、实际碰撞和玩家位置分离。低 TPS、客户端掉帧和长时间网络停顿仍可能造成停顿，这套补偿不改变游戏的 tick 频率。

恢复传送只用于读档或离线乘客归位，偏移按玩家实际身体宽高限幅，避免把身体塞入墙壁或顶板。在线玩家正常离开后立即移出名册。

## 4. 门、队列和异常行为

| 状态 | 行为 |
| --- | --- |
| OPEN | 完全开门，等待停留计时与新请求；停留到点**一律**关门（无请求时关着门停在本层待命） |
| CLOSING | 门进度从1降至0；门口有人则重新开门并保留请求 |
| MOVING | 门必须为0；每 tick 验证轨道与扫过的空间 |
| OPENING | 到站后门进度从0增至1 |
| BLOCKED | 停止移动；障碍恢复且目标有效时继续。读档后"名册里的乘客还没回到世界"也走这一相位（上限 `RIDER_WAIT_TICKS`）。**这一相位同时表示"故障"**：开门键变可用，乘客可以主动开门脱困（见下节） |

读档时轿厢保存的 `MOVING` 一律降级为 `BLOCKED`，先重验线路再继续；如果存档里带着乘客名册（`Riders`），会先保持静止等这些人回到世界：轿厢是区块实体、随区块载入，而玩家实体由登录流程单独载入、必然更晚，抢跑会让乘客被留在已经空掉的井道里掉出电梯。等待期间名册里的乘客一在井道里出现就被按存档偏移放回厢内；名册齐了、等待窗口用尽、或车上已经有别的乘客要走，就立刻放行继续原行程。

### 4.1 故障脱困与恢复

轿厢只要"现在走不了"，就算处于故障，**开门键变可用**，而且**不要求轿厢停在站点上**——它多半正卡在
两层之间，只有允许开门，被困的乘客才能自己走出来。故障包含下面四类：

| 故障 | 表现 |
| --- | --- |
| 运行途中被挡 | 断轨、朝向不一致、井道里有方块或实体障碍、区块未加载 → 相位转 `BLOCKED`，目的站保留 |
| 目的站的门被拆 | 目的站失效被清空 → 相位转 `BLOCKED` |
| **停着但线路没了** | 轨道或整条线路上的门被拆光，`line()` 扫不出线路 → 相位停在 `MOVING` 且无目的站。**这辆车永远不会再动了**（既不可能被派车、也不可能到站开门），必须按故障处理，否则生存模式里进来的人就出不去了 |
| 读档等乘客 | 名册乘客尚未归位 → 相位同样停在 `MOVING`，目的站还在 |

判定方式是 `Environment.canResume()`（= "上一次让 `canMove` 返回 false 的原因是否消失"），**不是相位**：
乘客开门脱困会把相位从 `BLOCKED` 改成 `OPENING`/`OPEN`，拿相位当判据会把"门刚开"误判成"故障已解除"，
门还没开就被同一刻关回去。反过来，故障块里也**绝不能因为"故障仍在"就 `return`**——那会把开门动画本身
挡掉（面板一直显示"正在开门"、门却停在起始位置）；故障期间门该怎么动就交给 switch 正常推进。
`canResume` 与 `canMove` 共用同一段判据（`pathClear`），因此不会出现"状态机以为通了、实际 `canMove`
仍然拒绝"的分叉；反过来，只要 `canResume` 为假就登记故障，所以上面四类都不会漏。
`canResume` 为假且"停着没行程"时还会把相位摆成 `BLOCKED`，让客户端显示"暂停：请检查轨道或障碍"。
区块未加载时 `canResume` 返回 true，不会把"暂时看不到"误判成"线路没了"。

`canResume` 有两处必须注意，**两处都会导致"按了开门键、门一晃又被关上"**（都由实机逐刻日志定位）：

1. **探测范围必须覆盖"到目的站那一段"**：`pathClear` 的扫掠体积取自"本刻位移"，若按"原地一步"调用
   （`pathClear(getY(), getY())`），位移为 0、**井道障碍根本不参与判定**，只要目的站还在就恒返回 true。
   因此有目的站时按 `pathClear(getY(), target.y())` 判整段。
2. **`target == null` 时绝不能看"相位是不是 `BLOCKED`"**：乘客按开门键会把相位改成 `OPENING`/`OPEN`，
   拿相位当守卫时它会在门一开的瞬间失效、`canResume` 翻成 true，于是把刚开满的脱困门立刻关回去。
   实测日志正是这个序列（**故障车**那一侧，`target` 始终为空）：

   ```
   phase=OPENING door=0.95 target=-  →  phase=OPEN door=1.00 target=-  →  phase=CLOSING
   ```

   正确判据只看"**有没有可恢复的行程**"：`target == null` 且相位仍是 `MOVING`（真正的空闲待命、
   关着门停在本层）才按"线路还在吗"判定；相位在 `OPEN`/`OPENING`/`CLOSING` 说明门正开着、
   而目的站为空（门被拆 / 整条线路被拆光）——**没有任何可恢复的行程**，必须返回 false 让门稳定开着。

| 时刻 | 行为 |
| --- | --- |
| 故障**仍在**、乘客按了开门键 | 门**照常动画打开并保持开着**（故障期间绝不在这里 `return`——否则开门动画本身被挡掉，会出现"面板一直显示正在开门、门却不动"）。门开着期间车不会移动：`MOVING/BLOCKED` 分支开头就有 `if (door > 0) break;` |
| 乘客按"关门" | 照常受理：门关上后可再按开门 |
| 运行途中（正常） | 开门键**不可用**，即使高度恰好经过某个整数楼层也不会闪一下可用（要看相位，不能只看坐标） |
| 故障解除的那一刻 | 若故障期间开过门，先把门关回去（`CLOSING`），关到全闭后才继续原行程；若一直没开门，立刻继续，不多做任何动作。判断条件是 `canResume && recoveryOpen && 门还开着`——**必须带上"门还开着"**，因为 `canResume` 在乘客把门打开之后常常就变真了（门开着时路径本来就通畅），少了这一条就会"按了开门键、门一晃又被关上" |
| 恢复后 | 目标与队列都还在（目的站被拆而清空的情况除外），行程按原计划继续；开门键回到"必须停稳在站点上"才可用 |
| 故障解除时相位的复位 | 清掉故障的标志时**必须同时把相位从 `BLOCKED` 复位回 `MOVING`**。`BLOCKED` 是"故障期"的显示相位：不复位就会出现"客户端看相位仍是 `BLOCKED`（暂停）→ 开门键保持可用，而服务端 `faulted` 已是 false → 拒收开门键"，表现为按钮亮着、点下去却弹"开门键只在轿厢停在某一层时有效"（实机踩过）。复位后由 `MOVING` 分支自然继续行程；门若还开着，那一分支开头的 `if (door > 0) break;` 会先把它关完 |

楼层门联锁也跟着放宽：`LandingDoorBlock.dockedCabin` 不再按相位排除 `BLOCKED`，而是继续用
"轿厢门进度 > 0 且轿厢精确停在该站"（1e-7 格）把关。否则故障时轿厢门开了、楼层门却拒绝交出碰撞，
人仍然走不出去。轿厢停在楼层之间时高度对不上，楼层门照旧不参与，不会半空开门。

**从轿厢走出去之后还会不会被拉回来？** 不会。只要门是开着的（`DOOR ≥ 0.999`），玩家一旦离开轿厢的乘客判定盒，
下一刻的名册维护就把他划掉，因此故障脱困走出去、或正常到站走出去，都不会在名册里留下"待归位"记录，
更不会在电梯修好后把人传送回轿厢。名册只在两种情况下留人：① 玩家**掉线**（或去了别的世界）——他没有能力
自己走出去，只可能是被行程丢下的；② 读档那一瞬间所有人还没载入完。两种情况都受 `RIDER_WAIT_TICKS`
（30 秒）上限保护，等不到就照原计划继续，不会把电梯永久钉死。

### 4.2 轿厢内的右键：面板与准星

轿厢是 3×3×3 的**空心壳**，它的碰撞几何（地板、顶板、侧壁、两扇滑门）同时被原版当作"准星能命中的实体形状"。
于是乘客在厢内看侧壁、后壁或门框时，射线常常穿到轿厢**后面的方块**上，这次右键就成了"对世界用物品"——
手里拿着方块时更是直接把方块放出去，实体交互根本轮不到。

处理它的是客户端 mixin `CabinCrosshairMixin`（注入 `GameRenderer.findCrosshairTarget`）。它同时维持两条行为：

| 情形 | 准星 | 结果 |
| --- | --- | --- |
| **乘客在厢内**，点轿厢的任何地方 | 改写为"命中本厢" | 右键**开面板**——不分位置、**与手里拿什么完全无关** |
| **门完全打开**、且原准星被轿厢接住，而只做方块射线时命中点**在轿厢之外** | 让给那个方块 | 射线**从门洞穿出去**：左键拆、右键放/交互都正常（故障脱困时"门口有方块挡路"就靠这条拆掉） |
| 门**关着或正在开关** | 一律命中本厢 | **射线不穿透轿厢**——门扇是真实阻挡，符合"点击射线不能穿透电梯轿厢" |
| 站在**外面**的玩家 | 原样 | 空手右键开门面板、潜行右键回收**不受影响**（判据是"命中的是不是自己所在的这辆轿厢"） |

穿透判据是**沿射线比较距离**：方块命中点比"射线打到**静态舱体**（地板、顶板、两侧壁、背板）"更近，才算穿出去。

- 为什么用**静态舱体**而不是完整碰撞集合（`collisionBoxes()`）：乘客朝门外看时，射线**必然先命中轿厢自己的门扇**
  （关着或半开都一样）。把门扇算作遮挡物，"从轿厢里打楼层门"就永远失败——楼层门在门扇之外。
  因此新增 `collisionBoxesStatic()` 专供准星穿透判定；**玩家身体的碰撞仍用完整集合**，照样被门扇挡住。
- 为什么**不能**用"方块坐标是否在轿厢包围盒之外"（曾经这么写，实机踩坑）：楼层门的方块坐标就落在轿厢
  3×3×3 的包围盒**里面**（轿厢盒跨 ±1.5 格、门在正面 1.3~1.5 那一带），那条判据恒为假、穿透永远取消，
  表现为"从轿厢里怎么都打不到电梯门"。用距离就没有这个问题。
- **"乘客的准星永远不会被改写到门外的方块上"**——穿透分支只在门开着、且原结果就是"命中本厢"时才生效，
  因此"点轿厢开面板"不会失效。

**关于电梯门（楼层门）打不掉**：门扇的碰撞形状随开门进度连续变化（`LandingDoorGeometry.shape`），
门**完全打开**时两扇宽度归零、**门洞中央没有任何碰撞形状**。所以门开着时站在轿厢里对着门洞中央，
射线会直接穿进候梯厅（那正是上一条穿透生效的结果）——**那个位置此刻没有门可打**。
要拆门请瞄**左右门框柱**（各 0.1875 格宽）或**门楣**（门洞上方 0.1875 格）；`LandingDoorBlock.onBreak`
的逻辑是"拆任意一格 → 整扇门一起拆"。

服务端 `AbstractCabinEntity.interact` 与之对应：**乘客无条件开面板**（所以只要有交互包送达就会开）；
非乘客只收到一条"请进入轿厢"的提示，并返回 `PASS` 把点击让给身后的方块。

**这只改"准星的实体命中"，不改碰撞几何**：玩家的身体照样被门扇与舱壁挡住。

**历史教训（都不要回去）**：为了让"只有戳在操纵面板上才开面板"，先后试过四种判据，全部在实机翻车：

| 写法 | 症状 |
| --- | --- |
| "水平视线 · 侧壁法线"方向点积 | 约 53° 的方向锥，**脸朝那一侧就"指哪都算"**，点门外方块也开面板 |
| 视线与**轿厢包围盒**相交 | 包围盒包含整个厢体，朝后壁、顶板、门框都会被判成在看面板 |
| 视线与**面板盒**相交（`PANEL_LOCAL_BOX`） | 面板渲染几何横跨局部 Z 0.20..0.90（占门洞宽度 0.48 格），朝着那一侧随手一点就命中 |
| 客户端每帧刷新、**限时若干刻的"正在看面板"标记** | **看过一眼面板后转身点别处**，标记还没过期就被那次右键消费——表现为"手里拿着东西点哪都能唤出面板" |

结论：在 3×3×3 的空心壳里，用射线几何区分"面板"与"别处"的容错窗口太小，收益不抵复杂度，因此
**面板采用"乘客点哪都开"这条简单规则**。相关常量（`PANEL_LOCAL_BOX`、`PANEL_FACE_TOLERANCE`）已随实现一并删除。

按**运行方向上的位置顺序**处理请求（不是按键先后）：同一方向上更近的楼层先停，因此上行途中不会越过同方向的楼层去更远的那层；重复的同一门请求合并。厅外呼叫带方向，只有正在按该方向运行的轿厢才顺路接走它；两侧都没有顺路请求时按距离兜底（空车去接反方向的孤立呼叫），保证任何请求最终都会被服务。请求删除或不完整的门会被拒绝；已排队但被拆除的门被移除，被拆门所在站的厅外呼叫也一并取消。运行中目的门拆除会暂停，避免半空开门；新的有效请求可以恢复运行。断轨、朝向改变、多个轿厢、实体/方块障碍、世界边界和区块加载状态也会影响移动。

不会主动加载区块，没有能耗、载重量、横向转弯和站点自定义名称参数。加速度与减速度由 S 形曲线的
`CRUISE_RAMP_TICKS` 与巡航速度共同给定（不再是"匀速、无加减速"），插值仍然只用于平滑显示。

| 运行状态判定 | 由同步数据推导，无额外同步字段：只有 MOVING 且有目的站才判上行/下行（比当前高度高＝上行、低＝下行，差值小于 `SYNC_POSITION_EPSILON` 视为已到站），其余相位（开门/开门中/关门中/暂停/关着门停靠）一律"停靠"（`logic/ElevatorStatus`） |
| 翻译键 | `status.easyelevator.up` = 电梯上行、`status.easyelevator.down` = 电梯下行、`status.easyelevator.idle` = 停靠（`en_us` 为 Going up / Going down / Parked） |
| 楼层号规则 | 站点按高度升序；**基准层 = 1 层**、其上 2、3…、其下 B1、B2…（内部负数，未设基准层时最低站点 = 1 层）。上行取"已到过/经过的最高一层"、下行取"已经过的最低一层"，因此只在经过或到达一层时变化一次；尚未经过任何站点时显示 `--`。三处显示同源：选站面板按钮、轿厢内面板、楼层门框顶部（`logic/FloorIndicator`） |
| 基准层设置 | **潜行右键**任意一扇完整的楼层门 → 弹出的是**该门专属设置面板**，在里面点「设为基准层」把它设为 1 层；同一线路其它门的标记会被清掉，拆掉基准门即回到默认编号。轿厢每刻扫描线路上的门方块实体取得它，因此改完下一 tick 三处显示全部跟上 | `LandingDoorBlock.openDoorSettings/setFloorBase`（面板按钮发 `SetBaseFloor` 包）、`AbstractCabinEntity.baseFloorY/updateFloorNumber` |
| 到站清扫 | 到站开门时**只清"本次服务方向"上的厅外呼叫**（方向取目的站本身：目的站来自厅外呼叫就用那条呼叫的方向，来自轿厢内选站就用行驶方向；读档恢复的行程没有这个信息，退回按行驶方向清）。同一层的另一方向呼叫**保留**：真实电梯的上/下呼叫灯各自独立，它要等轿厢回头再来接。目的站恰好就是本层时（门开着、另一方向有人按）就地认领并续满停留时间，不白关一次门 | `ElevatorController.serveStation/targetHallDirection`、`tick(OPEN)` |
| 厅外呼叫面板 | 右键楼层门弹出（不再直接呼叫）：方形按钮竖排——▲ 上行、▼ 下行、× 关闭（20×20 自绘方块，配色与选站面板的楼层键同源，**呼叫未完成时画成红色**，到站开门那一刻服务端推送新状态、按钮恢复）。**端站只显示有意义的方向**：最底层只有 ▲、最顶层只有 ▼（服务端按线路站点序号算好，随 `OpenHallPanel.showUp/showDown` 下发），中间层两个都在 | `client/LandingDoorScreen`、`LandingDoorBlock.openHallPanel`、`ElevatorNetworking.OpenHallPanel/HallPanelState/HallCallButton` |
| 停靠计划高亮 | 目的站 + 队列中的站点，服务端在计划变化时用 `PanelState` 推送（到达、取消、新请求），只影响已打开的面板 |
| 底部按键 | `<` `>` 翻页（首/末页禁用）、开门、关门、完成；开门/关门按轿厢实时状态自动禁用（无轿厢、不在站点、门已关好等） |
| 开门键语义 | 停稳在某个完整站点时受理（等于"请求当前这一层"）；门已全开时按下只续满停留时间；**处于故障（`BLOCKED`）时也受理**，让被困在两层之间的乘客能开门脱困（`AbstractCabinEntity.doorCommand`） |
| 关门键语义 | 立刻结束停留并关门，队列为空也允许（落点与停留自然结束一致：关着门停在本层等待）；关门中仍逐刻检查门口是否有人，防夹照旧（`ElevatorController.forceClose`） |
| 面板有效性判定 | UI 用宽松判定（水平 ±1.5 格、相对轿厢底 -0.6..+2.9 格）以免下行时被误判为已离开轿厢；权限校验始终在服务端（`ElevatorScreen.staysInside`） |
| 面板最大解码站点数 | 16384，`ElevatorNetworking.MAX_STOPS` |
| 服务端选站验证 | 活着、非旁观、身处指定轿厢、完整电梯门仍存在且同线路 |
| 面板背景 | 轻微暗色遮罩，不调用原版模糊着色器 |
| 显示高度 | 面板保留1位小数；仅显示，不降低运行精度 |
| 内部交互 | 主手右键选站，潜行时不抢占普通方块/物品交互 |

| `EVENT_VOLUME` | 0.8，到站提示音与试听的音量 |
| `RUNNING_VOLUME` | 0.6，随轿厢循环音量 |
| `SOUND_PITCH` | 1.0，原音高 |
| 声音分类 | BLOCKS，受游戏“方块”音量控制 |

| 到站音效 | `easyelevator:elevator_arrival`（也是门设置面板里"默认音效"那一项的来源） |
| 开关门音效 | **已移除**：开关门不再发声，`sounds.json` 里只保留运行/到站/自定义到站三个 ID |
| 到站音效选项数 | `DoorSounds.CHOICE_COUNT` = 8：0 默认音效、1 自定义文件、2..7 六组预设原版音效（钟回响/紫水晶风铃/音符盒铃/音符盒叮/经验球/末影之眼） |
| 到站音效默认开关 | **开 + 默认音效**（`DoorArrivalSound.DEFAULT`）：等于模组原有的"到站必响一次"，**升级后行为不变**——本功能之前放置的门存档里没有 `ArrivalSound` 键，`readNbt` 对**缺失的开关回退到出厂默认（发声）**，因此旧门照旧会响，不需要逐扇重设。存档只在玩家**关掉**开关时才写 `ArrivalSound=false`，整份默认设置的门一个字段都不写（体积与加这个功能之前一致） |
| 到站音效作用域 | **按门**：音色取自轿厢当前停靠的那扇楼层门（按同高度匹配 `ElevatorLine.stops()`），不是轿厢自身 |
| 自定义音频上限 | `MAX_AUDIO_BYTES` = 512 KiB/文件，必须是 Ogg 容器（校验 `OggS` 魔数，不只是扩展名） |
| 门槽上限 | `DoorSounds.MAX_SLOTS` = 64＝运行时资源包里最多 64 条自定义到站音效声明 |
| 门槽推导 | `DoorSounds.slotFor(x, y, z)`：先用三个大步长常量把 x/y/z 混进一个 long，再做一次 murmur3 收尾混合，最后 `Math.floorMod(h, MAX_SLOTS)`。纯函数、不占存档字段；**不能**直接用 `BlockPos.hashCode() % MAX_SLOTS`（那个 hashCode 的分布会让相邻坐标频繁撞槽）。撞槽时两扇门共用同一段音频（可接受的退化） |
| 权威副本目录 | `config/easyelevator/arrival_sounds/arrival_<槽>.ogg`（服务端与客户端各存一份，由网络层搬运） |

| 资源重载时机 | **只在内容指纹变化、或包刚被启用时**重载一次；进存档而不改音频时一次都不重载（这是"每次进存档闪红屏"的根治点） |
| 门设置同步范围 | 站点周边 **64 格**内的玩家（与厅外呼叫灯同一范围） |
| 试听高亮 | 值格的音效名加 `▶` 前缀，保持 `FLASH_TICKS` = 12 帧（按帧递减，约 0.2 秒） |
| 门动画接口 | 轿厢门 `cabin.doorProgress(tickDelta)`；楼层门门扇 `doorEntity.openProgress(tickDelta)`，0全关、1全开，两者逐刻同值 |
| 扩展事件 | `ElevatorEvents.PHASE_CHANGED`、`ARRIVED` |

音效资源默认静音；具体 OGG 和模型替换步骤见 [ASSET_INTEGRATION.md](ASSET_INTEGRATION.md)。
**每扇门各自的到站音效**（含上传本地 `.ogg`）见 [README](../README.md) 的「每扇门自己的到站音效设置」一节。

存档保存 RailX、RailZ、Facing、Phase、Door、Target、Queue、HallCalls（厅外呼叫：站点坐标 + 方向）与 Travel（当前服务方向），以及原版实体坐标。基准层标记写在**基准门自己的方块实体 NBT** 里（随区块存档），不占轿厢字段；**每扇门的到站音效设置也写在同一个方块实体 NBT 里**（`ArrivalSound` / `ArrivalSoundChoice`），且**只在偏离出厂默认时才写**，因此整份默认设置的门存档体积与加这个功能之前一致。上传的音频不写存档，落在 `config/easyelevator/arrival_sounds/`（见上表）。**轿厢型号（普通/高速/观光）不写进存档**：它由实体类型唯一决定，读档时按注册类型重建，因此速度与玻璃外观永远与物品一致，也不会出现"存档里写坏了速度"的情况。客户端插值样本属于临时显示数据，不写进存档。沿用旧存档字段，**2.2.0 可读取之前的轿厢**（旧的 `easyelevator:cabin` 就是现在的普通型号，行为不变）；旧按钮需要按距轨道 3 格重新放置为完整电梯门，旧队列中的无效位置会被过滤；改动存档字段或几何尺寸前先备份世界。

## 7. 修改后的验证

改参数 → `build` → 客户端上下各乘一次 → 多人同时乘坐测试。重点确认相机与地板没有相对抖动、
最终高度准确、障碍不会穿越、门口防夹正常。工程内**没有常驻自动化测试**（`test` 任务被关闭），
逐项检查表见 [人工验收清单](TESTING.md)。另有一套**可选开启**的乘客回归测试
（`src/gametest`，加 `-PriderTests` 才构建，见 [构建与打包](BUILD_AND_PACKAGING.md)），
但它只覆盖乘客移动与历史补偿这类可自动化的回归，不替代手感验收。

改 `HIGH_SPEED`、`CRUISE_RAMP_TICKS` 或 `MAX_ACCELERATION`（或新增第四种型号）后至少确认：
① `巡航速度 + POSITION_EPSILON ≤ 1 格` 仍然成立（否则单刻位移可能跨过整格站点、到站吸附失效）；
② 三种型号的加/减速手感（加/减速段各 `CRUISE_RAMP_TICKS` 刻，距离 = `速度 × T / 2`：普通 3.2 格、高速 8.0 格）；
③ 到站仍精确停在楼层高度、运行途中门保持关闭、开关门与停留时间不变。

## 8. 版本变更要点

### 8.1 2.2.0：乘客自主移动与网络延迟补偿

- 正常载客**移除逐刻传送**，只叠加平台的竖直位移，玩家自己的行走、跳跃速度与落地状态全部保留。
- 客户端在玩家物理更新**之前**统一推进轿厢与乘客（`client/CabinMotion.beginPlayerTick`），
  渲染、碰撞与玩家共用同一组位置样本；**不再单独锁定镜头**（旧的相机补偿混入已删除）。
- 乘客移动包（`rider_move`）附带其所用的**轿厢样本编号**；服务端以自身历史位置补偿网络延迟
  （`logic/RiderMotionHistory`），再交给原版移动包路径做速度、碰撞与传送确认检查。
- `MotionFrame.riderOffset` 字段**保留但客户端已不再使用**（客户端改为自行判定乘客是否为乘客），
  属于兼容字段——它不再驱动任何镜头行为。
- 修复到站切换 `OPENING` 时漏掉乘客最后一步位移，以及在线离厢被存档名册误拉回的问题。
- 静态轿厢与门洞尺寸未改；**服务端与所有客户端必须一起升级到 2.2.0**。

### 8.2 2.1.1：多人同步与离厢规则

- 不改变速度、门时序和插值缓冲参数。
- `OpenDoorPanel.open` 仅在**主动打开**时为 true；广播为 false，只刷新同站点已打开的面板。
- 离厢与归位的判据**只看"在不在厢内"，不看相位、也不看门进度**：在线玩家一旦不在厢内就立刻移出名册
  （包括开门过程中走出去、以及故障脱困走出去）；只有**掉线**（或去了别的世界）的玩家会被标记为
  "待归位"并留在名册里，等他在同一条井道里重新出现时按存档偏移放回。
- 楼层门启用动态碰撞（方块注册时的 `AbstractBlock.Settings.dynamicBounds()`），碰撞查询直接读取
  当前门进度，不再受同刻旧样本影响。
